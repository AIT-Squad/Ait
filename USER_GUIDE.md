## 1. Quickstart

### 1.1 Install

```bash
git clone <repo> && cd Ait
python install.py                      # install to ~/.claude/skills/ait
python install.py update               # upgrade (keeps .venv, fast)
python install.py update --skip-venv   # files only
python install.py uninstall
python install.py --prefix /custom/path
```

On first run, `bin/ait` creates a `.venv` inside the skill directory and installs its
dependencies — no manual setup needed.

Once installed, **you never touch the CLI directly**: everything is done in Claude Code with
slash commands (`/ait <subcommand>`), as the next section explains.

### 1.2 Usage: `/ait <subcommand>`

AIT is a Claude Code Skill. All day-to-day operations are issued in Claude Code as
**`/ait <subcommand>`** — the skill layer routes them to the underlying CLI:

| Scenario | What the skill layer actually calls |
|---|---|
| First `init`, or `init --refresh-wrapper` after a path change | `~/.claude/skills/ait/bin/ait` |
| **All** other commands | `project-docs/.ait/ait-cli` (the project-local wrapper generated by `init`; `ait-cli.cmd` on Windows) |

**There is no system-wide `ait` command** — don't assume `ait` is on PATH. Don't bypass the
skill and type the CLI directly either, unless you are debugging the CLI itself.

All examples below are written as `/ait <subcommand>`.

### 1.3 Working directory

Always run from the **directory containing `project-docs/`** (the project root):

```bash
cd /path/to/my-project      # has a project-docs/ subdirectory
```

Then in Claude Code:

```text
/ait state
```

- Running inside `project-docs/` → `CWD_INSIDE_PROJECT_DOCS`
- No `project-docs/` in the current directory → `NOT_AT_PROJECT_ROOT` (`init` is the exception — it creates it)
- `project-docs/` exists but lacks `docs/` or `.meta/` → `PROJECT_DOCS_MALFORMED`

The directory name `project-docs` is hard-coded: no `--project`, no `AIT_ROOT`, no upward
marker-file search.

### 1.4 Output contract

Every command prints exactly **one JSON object** on stdout:

```json
{"ok": true,  "data": {...}}
{"ok": false, "error": "human-readable reason", "code": "STABLE_ERROR_CODE"}
```

Hints go to stderr and never pollute stdout. When scripting, branch on `code` — never parse
the `error` text.

## 2. Core Mental Model

### 2.1 The chunk is the smallest unit

Documents are cut into chunks by `<!-- @id:xxx -->` annotations. Versioning, relations,
merging and locking all operate on chunks, not files. Different chunks in the same file can
be in different states.

### 2.2 Zero relation declarations in document bodies

PRD/FSD/TDD markdown bodies **carry no chunk-to-chunk relations**. The four relations live
only in the SpecGraph, each born atomically from one command:

| Relation | Meaning | Birthplace |
|---|---|---|
| `derives` | PRD root → root FSD (problem → solution) | `fsd create --parent <PRD-root>` |
| `decomposes` | FSD split → child FSD root (split downward) | `fsd decompose <parent> <child>` |
| `details` | leaf FSD split → TDD root (refine) | `tdd create --parent <split>` |
| `depends_on` | dependency between sibling splits under one parent | a `depends_on:` yaml block inside `fsd create` content (stripped from disk once the edge exists) |

There is no `link` command and no `depend` command. `target_file` is a chunk→file attribute
(not a chunk-to-chunk relation), so it stays in the TDD body.

### 2.3 One open version at a time

`version create` is the only way to open a version. With an unmerged version active you get
`ACTIVE_VERSION_EXISTS` — the previous version must be merged or reverted first. Reusing an
existing version name also errors: no ghost versions.

### 2.4 Three-state locking

A chunk moves through `working → staged → committed` inside the version workspace:

- **working**: freely rewritable (same id replaces in place)
- **committed**: frozen for this version; further edits get `CHUNK_LOCKED`
- A layer's `confirm` freezes that layer; its `revert` unlocks it for rework

### 2.5 Strict top-down (the phase machine)

```
empty ──prd create──▶ prd-creating ──prd confirm──▶ prd-confirm
      ──fsd create/decompose──▶ fsd-creating ──fsd confirm──▶ fsd-confirm
      ──tdd create──▶ tdd-creating ──tdd confirm──▶ tdd-confirm
      ──version merge──▶ merged
```

Every write entry point checks the phase first; violations are refused with **zero disk
writes** (fix in place and retry). Changing any layer means walking down from the PRD —
`add` and `modify` go through identical gates, iteration included.

### 2.6 confirm and merge are separate

- `version confirm` = **gate + plan**: runs the six invariants + artifact-scope governance +
  artifact acceptance, then freezes a reconciliation plan with an input fingerprint.
  Repeatable; writes no document content; lands nothing into the baseline.
  Note (v2.73): after the gate passes, if the host repo has uncommitted changes, confirm
  **commits the host repo** as `AIT <v> artifacts` and binds `code_result` — dirty is no
  longer a reason to refuse; it's a reason to commit.
- `version merge` = **the only landing point**: executes the confirmed plan; any failure
  rolls back byte-for-byte.

The plan carries an input fingerprint; if version content changes after confirm, merge
reports `CONFIRMATION_STALE` and demands a fresh confirm.

### 2.7 Docs repo / code repo isolation

`project-docs/` is **its own git repository**, excluded from the host repo via `.gitignore`.
AIT commits never touch your code history. `version merge` records the cross-repo binding:
`docs_commit` (docs-side commit), `code_base` (host HEAD at merge time), `code_result`
(host HEAD after acceptance), plus the persistent revert anchor `refs/tags/ait/<v>`.

### 2.8 Layered config

| Layer | File | Contents | Committed? |
|---|---|---|---|
| Shared | `.meta/config.yaml` | `initialized`, `auto_snapshot_on_merge`, `artifact_scopes` | Yes (docs repo) |
| Machine-local | `.meta/config.local.yaml` | `skill_dir`, `cli_path`, `wrapper_path`, `acceptance_command` | No (git-ignored) |

Reads merge both layers with the local layer winning. **A layer that exists but is corrupt
raises `CONFIG_UNREADABLE` and never degrades to an empty config** — otherwise a
config-dependent acceptance gate would mistake "cannot read" for "not configured" and let
the merge through.

## 3. Project Bootstrap

### 3.1 Starting from an empty directory

```bash
mkdir my-project && cd my-project
```

Then in Claude Code:

```text
/ait init --new-model --name my_project
```

One command does all of this:

1. Creates the `project-docs/` skeleton (`docs/`, `.meta/versions/`, `.meta/changes/`)
2. `git init` inside `project-docs/`; appends `project-docs/` to the host `.gitignore`;
   the docs repo's own `.gitignore` excludes `versions/*/state.md`, `.meta/snapshots/`, `.ait/`
3. Writes `docs/prd/[PRD]-my_project.md` and `docs/fsd/[FSD]-my_project.md`
4. Creates the PRD→FSD `derives` edge in the SpecGraph
5. Lays down empty baseline stores (`chunks-index.yaml`, `specgraph.yaml`) — the initial
   state is an iteration whose current state is empty; zero special cases
6. Generates `project-docs/.ait/ait-cli` and writes the config paths

`--name` accepts only lowercase alphanumerics/underscores with dash segments (it must form a
legal chunk id); uppercase/spaces/CJK/`/`/`..` get `INVALID_PROJECT_NAME`. Existing user
files are never overwritten (idempotent).

### 3.2 Common options

| Option | Effect |
|---|---|
| `--new-model --name N` | New-model baseline (PRD/FSD/TDD) — **recommended** |
| `--check` | Only diagnose `docs/global` state (fresh / incomplete / ready); writes nothing |
| `--refresh-wrapper` | Only refresh skill paths and the local wrapper; documents untouched |
| `--skip a,b` | In incremental mode, mark global items the user explicitly skips, avoiding repeated prompts |
| `--migrate [--apply]` | Docs-repo hygiene migration: untrack historically committed `.meta/snapshots/` and `.ait/`, move machine-specific config to the local layer. Preview by default |

`--migrate` with `--apply` alone reports `USAGE_ERROR`; it is an independent sub-mode and
does not run regular initialization.

### 3.3 Skill path changed?

After reinstalling the skill or moving machines:

```text
/ait init --refresh-wrapper
```

When the wrapper is missing or `AIT_SKILL_DIR` drifts from the config, the CLI prints a tip
on stderr (JSON output unaffected).

## 4. The Full Pipeline

```text
/ait version create v0.1                       # open a version

/ait prd create "[PRD]-app"                    # ① no content → discussion background + context_token
#   ...discuss with the AI until converged...
/ait prd create "[PRD]-app" --action modify \
    --content-file prd.md --context-token ctx-v1.<digest>
/ait prd confirm                               # freeze the PRD layer

/ait fsd create "[FSD]-app" --parent "[PRD]-app" \
    --content-file fsd.md --context-token ctx-v1.<digest>
/ait fsd decompose "[FSD]-app:core" "[FSD]-core" \
    --content-file core.md --context-token ctx-v1.<digest>
/ait fsd confirm                               # freeze the FSD layer

/ait tdd create "[TDD]-parser" --parent "[FSD]-core:parse" \
    --content-file tdd.md --context-token ctx-v1.<digest>
/ait tdd confirm                               # freeze the TDD layer

/ait codegen prepare "[TDD]-parser"            # focused context → AI writes the code

/ait acceptance set "uv run pytest -q"         # configure the artifact acceptance command
/ait version commit v0.1                       # working → committed
/ait version confirm v0.1                      # gate + reconciliation plan (commits host artifacts if dirty)
/ait version merge v0.1                        # the only landing point + docs repo commit
```

Each layer follows a fixed order: **discuss → write → freeze**. Skipping a layer is refused
by the phase gate.

## 5. The PRD Layer

### 5.1 Discuss first, write second

Omitting `--content` / `--content-file` makes the command **write nothing** and return a
discussion background instead:

```text
/ait prd create "[PRD]-app"
```

Returns `mode: discussion-context`: the full text of every PRD chunk in baseline ∪ the
current version, the target chunk's existing content, and a `context_token`. An empty
baseline returns an empty background (the initial iteration has no special cases).

### 5.2 Writing with a token

```text
/ait prd create "[PRD]-app" --content-file prd.md \
    --action modify --context-token ctx-v1.<digest>
```

- `--action add` (default) / `--action modify`
- `--file <name>`: relative index path under `prd/`, without `.md`. Out-of-bounds values
  (path escape, wrong kind, suffix included) get `INVALID_FILE_NAME`
- `--overrides`: rename/redirect mapping; two records hitting the same target get
  `DUPLICATE_OVERRIDES_TARGET`
- `--context-token`: must match the background's intent, otherwise
  `CONTEXT_TOKEN_STALE` / `CONTEXT_TOKEN_CONFLICT`
- `--skip-context`: the explicit opt-out; mutually exclusive with a token; leaves an audit trace

### 5.3 What a PRD contains

**Zero technical content.** Overview, scope (included + **excluded**), user roles, goal
metrics, risks, plus requirement items (user story + what's out of scope + user-level
acceptance). Skeleton: `templates/TEMPLATE-PRD-AIT-DRAFT.md`.

### 5.4 Freezing

```text
/ait prd confirm      # locks [PRD]- chunks, phase → prd-confirm, drops a git anchor
/ait prd revert       # paired rework: unlock, phase → prd-creating
```

## 6. The FSD Layer

Prerequisite: phase must be `prd-confirm` or `fsd-creating`, otherwise `PRD_NOT_CONFIRMED`.

### 6.1 Deriving the root FSD from the PRD

```text
/ait fsd create "[FSD]-app" --parent "[PRD]-app" \
    --content-file fsd.md --context-token ctx-v1.<digest>
```

`--parent` makes the `derives` edge born atomically with creation. Without `--content` you
get a **discovery background**: the full text of `[PRD]-` chunks changed in this version +
one-hop neighbours of each anchor.

### 6.2 Decomposing downward

```text
/ait fsd decompose "[FSD]-app:core" "[FSD]-core" \
    --content-file core.md --context-token ctx-v1.<digest>
```

Atomically "write child FSD + create the `decomposes` edge". If the child chunk doesn't
exist yet and no content is given, you get an **anchored background**: the parent chunk's
full text + all adjacencies (with relation types and directions) + the upstream chain to the
PRD + the target's existing content.

Only an FSD split can be a `decompose` parent; PRD derivation goes through
`fsd create --parent` (misuse reports `INVALID_DECOMPOSES_TYPES`).

### 6.3 FSD file structure (recursively uniform)

Each FSD file = root + N functional splits + **exactly one `:TEST`**:

- **root**: the functional domain's responsibility boundary (what upstream it inherits, what
  it owns / doesn't own) + the decomposition view (child structure, no signatures)
- **functional split**: functional description + **capability contract (provide-only)**
- **`:TEST`**: integration acceptance for all chunks in the file combined. `:TEST` is the
  only uppercase split name allowed; all other split names are lowercase

**A capability contract states only "what this chunk provides"**: the provisioning form
(HTTP endpoint / module function / CLI command / event), the interface (methods, parameter
names and types, return structure, error semantics).

Never write "what it needs/depends on" (that's the `depends_on` relation, SpecGraph-only);
never write internal implementation (that's the TDD).

### 6.4 Declaring sibling dependencies

Declared temporarily inside a split's body; `fsd create` parses it, creates the edges, and
**strips the block from disk**:

````markdown
<!-- @id:[FSD]-app:feat -->
## feat module
```yaml
depends_on: [store, config]
```
````

- Shorthands resolve within the same parent (`store` → `[FSD]-app:store`); a full id must
  share the parent — cross-parent gets `DEPENDS_ON_CROSS_LEVEL`
- Naming a nonexistent sibling gets `DEPENDS_ON_UNKNOWN_SIBLING`; self-reference gets
  `DEPENDS_ON_SELF`
- **Preserve semantics**: a split without a `depends_on` block **keeps its existing edges**.
  Change = modify with the block; clear = explicit `depends_on: []`; untouched = no block.
  Rearranging prose never silently deletes dependencies

One FSD node **must not mix** FSD children (decomposes) with TDD children (details) —
that's `FSD_MIXED_CHILDREN`.

### 6.5 Freezing

```text
/ait fsd confirm    # phase → fsd-confirm
/ait fsd revert     # phase → fsd-creating
```

## 7. The TDD Layer

Prerequisite: phase must be `fsd-confirm` or `tdd-creating`, otherwise `FSD_NOT_CONFIRMED`.

```text
/ait tdd create "[TDD]-parser" --parent "[FSD]-core:parse" \
    --content-file tdd.md --context-token ctx-v1.<digest>
/ait tdd confirm
/ait tdd revert
```

`--parent` atomically creates the `details` edge; the parent must be a **leaf** FSD split.

### 7.1 target_file is mandatory

Every TDD root chunk must declare `target_file` in a yaml block (missing →
`TDD_TARGET_FILE_REQUIRED`):

```markdown
<!-- @id:[TDD]-parser -->
## parser tech design
```yaml
target_file: src/parser.py
```
```

- **Uniqueness**: two TDDs may not declare the same `target_file`
  (`DUPLICATE_TARGET_FILE`); comparison uses normalized paths (separators, `./`, and case
  variants count as the same artifact)
- **Any generation target works**: source, tests, templates, `SKILL.md`, scripts

### 7.2 What a TDD contains

`target_file`, tech-stack constraints, file responsibilities (owns + **does not own**), code
structure, core implementation logic, error boundaries, unit-test requirements. One TDD per
file.

**FSD vs TDD boundary**: the FSD is the black-box external interface (how others call it);
the TDD is the white-box implementation blueprint (how this file is built inside).

### 7.3 Three universal writing rules (PRD/FSD/TDD alike)

1. **Self-contained in full**: each chunk fully explains itself; no "see X" buck-passing
2. **Negative requirements are mandatory**: each chunk states what it does NOT implement /
   is NOT responsible for (and who owns that)
3. **Terms expanded in place**: summarizing terms are expanded at the point of use; no bare
   jargon, no central glossary

## 8. codegen & Artifact Acceptance

### 8.1 Getting the focused context

```text
/ait codegen prepare "[TDD]-parser"
```

What comes back is not the bundle itself but a small pointer (v2.74): `{bundle_path, sha256,
bytes, version, target_file, tdd_root, source_file}`. The full bundle (rendered text, v2.80)
is written to a **temp file outside the repo** (`$TMP/ait-codegen/<version>_<tdd>.md`, never
git-tracked); the orchestration layer reads that file and verifies the sha256 before
injecting it into the AI. Bundle contents: the TDD's body chunks, the full upstream chain to
the PRD along `details`/`decomposes`/`derives`, sibling capability contracts pulled along
`depends_on`, and the `target_file` with its **current content**. The target file state is
three-valued (v2.80): `absent` (legitimate new file) / `loaded` / `unreadable` (exists but
cannot be read — strictly distinguished from `absent` so existing code is never mistaken
for a blank slate and overwritten).

**`codegen prepare` does not write code** — it only assembles context; the Skill layer
drives the AI from there.

With an active version, phase must be `tdd-confirm` (otherwise `TDD_NOT_CONFIRMED`); with no
active version or a merged one, it resolves against the baseline with no gate.

### 8.2 Artifact acceptance

```text
/ait acceptance set "uv run pytest -q"   # written to .meta/config.local.yaml
/ait acceptance set                      # omitting the argument clears it
/ait acceptance run                      # run once manually, echoes passed
```

Once configured, `version confirm` and `version merge` run this command automatically before
landing (cwd = project root); exit ≠ 0 → `ACCEPTANCE_FAILED`, refused before anything lands.
Unconfigured means skipped.

The command lives in the machine-local layer: it gets executed, and paths differ per
machine — it must not travel with shared history.

## 9. Landing a Version: commit / confirm / merge

### 9.1 commit — lock

```text
/ait version commit v0.1 -m "message"
```

Bulk-pushes every `working` chunk in the version to `committed`. Further edits get
`CHUNK_LOCKED`.

### 9.2 confirm — gate + plan

```text
/ait version confirm v0.1 [--conflict-policy use-version|abort|use-baseline]
```

Checks:

1. All tasks `done` (vacuously true with no tasks)
2. Duplicate adds / override collisions
3. **The six invariants** — validated over the combined `baseline ∪ version` view
4. **Artifact-scope governance** (v2.83, only when `artifact_scopes` is configured):
   `TEST_SPLIT_UNCOVERED` / `UNCOVERED_ARTIFACT` / `TARGET_FILE_SCOPE_ESCAPE`, each
   configurable as `warn`/`block`
5. The **artifact acceptance** command
6. **Host artifact binding** (v2.73): host repo dirty → auto `git add -A` + commit as
   `AIT <v> artifacts` and bind `code_result`; clean → bind current HEAD; not a git repo →
   skipped without error

On success a **reconciliation plan** (with the fingerprint of every planning input) is
frozen and returned; on failure you get the violation details with `code` =
`INVARIANT_VIOLATION` / `ACCEPTANCE_FAILED` / `TASK_NOT_DONE` / `CONFIRMATION_FAILED`
(block-level governance violations).

Repeatable; writes no document content; lands nothing into the baseline — but it does
persist the plan and may produce a host-repo commit (see item 6).

### 9.3 merge — the only landing point

```text
/ait version merge v0.1
```

Flow: verify the plan is still valid (changed inputs → `CONFIRMATION_STALE`) → backup →
execute the plan chunk by chunk into the baseline → rebuild the baseline index and
SpecGraph → promote version edges to baseline → write the merged marker → docs-repo git
commit → record `docs_commit`/`code_base`/`code_result` and the revert anchor tag.

Failure at any step: **byte-for-byte rollback** (docs and `.meta` restored together),
reported as `MERGE_ROLLBACK`; no merged marker is left behind.

### 9.4 push — dual-repo publishing (v2.81)

```text
/ait push [--dry-run]
```

Publishes both repos to their remotes: **host repo first** (code artifacts), **then the
docs repo** (specs + `refs/tags/ait/*` anchor tags). The order guarantees "code visible
before specs"; a failed docs push can simply be rerun to converge. `--dry-run` only reports
what would happen.

### 9.5 Merge semantics (modify / add)

Each chunk is handled by its **actual existence**:

- **modify = full-chunk replacement**: the version side must provide the chunk's complete
  final content (bring along whatever should stay)
- **add = brand-new chunks only**: hitting an existing baseline chunk gets
  `DUPLICATE_BASELINE_CHUNK`
- A modify whose target is absent from the baseline is automatically treated as an add.
  **Merge never silently drops a chunk**
- Pre-flight interception: a modify renaming onto an existing id → `MODIFY_RENAME_COLLISION`

### 9.6 The three git-commit outcomes

- Not a git environment / git unavailable → tolerated; the result carries
  `git: "unavailable"` (no fake success)
- No changes → no-op; returns the current HEAD
- A real commit failure → `GIT_COMMIT_FAILED`, entering the rollback path

## 10. Rework & Rollback

### 10.1 Layer-level rework

Every layer's `confirm` is paired with a `revert` — **every gate has a rework path; there
are no terminal traps**:

```text
/ait prd revert      # prd-confirm → prd-creating
/ait fsd revert      # fsd-confirm → fsd-creating
/ait tdd revert      # tdd-confirm → tdd-creating
```

Unlocks that layer's chunks (committed → working) and rolls the phase back. Merged versions
refuse.

### 10.2 Whole-version exit

```text
/ait version revert v0.1 --confirm
```

- **Unmerged version**: physically wipes the version workspace and its indexes (no partial
  undo — this is the escape hatch of the atomic-version model)
- **Merged version**: `git reset --hard` the docs repo to that version's anchor tag, roll
  the host repo back to `code_result`, and delete all later version artifacts

Without `--confirm` it returns `NEED_CONFIRM` with an impact summary (which versions would
be deleted) and does nothing. An unusable anchor reports `REVERT_PRECHECK_FAILED` /
`REVERT_ANCHOR_INVALID`.

### 10.3 Anchor backfill (v2.72)

The tag is only a GC-safety optimization — **the commit SHA is the authoritative anchor**:
when a tag is lost, revert falls back to the `docs_commit`/`code_result` recorded in the
version meta and proceeds. To backfill tags for historical versions:

```text
/ait version backfill-tags    # idempotent: fills the missing, skips the present
```

## 11. Query & Diagnostic Commands

### 11.1 State panel

```text
/ait state                        # current version panel (markdown)
/ait state --version v0.1
/ait state --format json
/ait state --save                 # writes versions/<v>/state.md
```

Shows the version phase, chunk three-state distribution, PRD/FSD/TDD breakdown, and
next-step suggestions.

### 11.2 Relations & impact

```text
/ait deps "[FSD]-app:core" --direction both|in|out
/ait impact "[PRD]-app"                     # transitive impact closure
/ait specgraph query "[TDD]-parser" [--deps] [--implements]
/ait specgraph export --format dot
/ait specgraph graph-html [--version v0.1] [--prd-chunk "[PRD]-app:req1"]
/ait specgraph sync
```

`graph-html` generates a file-level spec tree: without `--version` it writes
`docs/graph.html`; with it, `versions/<v>/graph.html`.

### 11.3 Read-only validation

```text
/ait specgraph validate-new-model [--version v0.1]
```

Read-only diagnostics for graph legality + `target_file` uniqueness (also reports
`relation_residue` / `prd_requirement_residue` / `derives_residue` — report-only, never
blocking). **The authoritative enforcement is the confirm/merge gate**; this command just
surfaces problems early.

### 11.4 Search & rebuild

```text
/ait search "keyword" [--scope prd|impl|all] [--regexp]
/ait baseline-summary [--scope prd|impl|all] [--format yaml|json]
/ait reindex                      # rescan docs/, rebuild baseline index + SpecGraph
/ait context <chunk-id> [--scenario prd-to-impl|impl-edit] [--focus] [--deps]
/ait lint [--scope baseline|version|v0.1] [--fix]
/ait version status v0.1
```

`reindex` preserves explicit edges (`source: new-model-cli`) — rescanning never loses
relations.

## 12. Error Codes & Recovery

### 12.1 Environment

| Code | Cause | Recovery |
|---|---|---|
| `NOT_AT_PROJECT_ROOT` | No `project-docs/` in the current directory | cd to the project root; `init` new projects first |
| `CWD_INSIDE_PROJECT_DOCS` | Running inside `project-docs/` | Step up to the parent directory |
| `PROJECT_DOCS_MALFORMED` | Missing `docs/` or `.meta/` | Check the directory or re-`init` |
| `USAGE_ERROR` | Misspelled command/arguments | Output is still JSON; fix per `error` |
| `CONFIG_UNREADABLE` | A config layer exists but is corrupt | Fix the YAML syntax in `.meta/config*.yaml` |

### 12.2 Phase gates

| Code | Cause | Recovery |
|---|---|---|
| `NO_ACTIVE_VERSION` | No open version | `version create <v>` first |
| `ACTIVE_VERSION_EXISTS` | An unmerged version exists | Merge or revert it first |
| `VERSION_NOT_FOUND` | Version doesn't exist | `version create` (never auto-created) |
| `PRD_LAYER_CLOSED` | Creating while the PRD layer is frozen | `prd revert` to reopen |
| `PRD_NOT_CONFIRMED` | Writing FSD before `prd confirm` | `prd confirm` first |
| `FSD_NOT_CONFIRMED` | Writing TDD before `fsd confirm` | `fsd confirm` first |
| `TDD_NOT_CONFIRMED` | Running codegen before `tdd confirm` | `tdd confirm` first |

### 12.3 Context tokens

| Code | Cause | Recovery |
|---|---|---|
| `CONTEXT_TOKEN_REQUIRED` | Content write without a token | Call create without content first to get the background + token |
| `CONTEXT_TOKEN_INVALID` | Malformed token | Pass the returned value verbatim |
| `CONTEXT_TOKEN_STALE` | Background has changed | Re-fetch the background, re-discuss |
| `CONTEXT_TOKEN_CONFLICT` | Token intent doesn't match this call | Check target/parent anchor/file/action |
| `CONTEXT_SKIP_NOT_ALLOWED` | `--skip-context` on a contentless call | `--skip-context` is only for writes with content |

### 12.4 Relations & invariants

| Code | Cause | Recovery |
|---|---|---|
| `DUPLICATE_TARGET_FILE` | Two TDDs claim the same file | Give each its own file |
| `TDD_TARGET_FILE_REQUIRED` | TDD lacks `target_file` | Add the yaml declaration |
| `TDD_MULTI_PARENT` | TDD has a second FSD parent | One TDD takes exactly one details in-edge |
| `PRD_FSD_LINK_NOT_UNIQUE` | PRD root linked to multiple FSDs | Keep exactly one derives |
| `MISSING_ENDPOINT` | Edge points at a nonexistent chunk | Create the endpoint chunk first |
| `FSD_MIXED_CHILDREN` | One FSD mixes FSD children and TDD children | Be either a decomposition node or a leaf |
| `DEPENDS_ON_CROSS_LEVEL` / `_UNKNOWN_SIBLING` / `_SELF` | Dependency declaration out of bounds | Siblings under the same parent only |
| `INVALID_DERIVES` / `INVALID_DECOMPOSES_TYPES` / `INVALID_DETAILS` | Illegal relation endpoint types | See the relation table in §2.2 |
| `INVARIANT_VIOLATION` | Six-invariant violation at confirm | Fill in specs per `details.violations`, then re-confirm |
| `CHUNK_ID_PREFIX_REQUIRED` / `ID_FORMAT` | Illegal chunk id | Use `[PRD]`/`[FSD]`/`[TDD]` prefixes; `_` within names, `-` between segments |
| `PRD_REQUIREMENT_CONTRACT_VIOLATION` | PRD requirement chunk lacks a user story / an acceptance-criteria section / numbered items | Add the EARS items and rerun the same command (zero disk writes); the PRD root is exempt |
| `MARKDOWN_CONTAINS_RELATION` | New-model body retains `@ref`/`@extract`/relation declaration blocks | Relations live only in the SpecGraph; remove the residue and build edges via the four birthplaces |
| `TEST_SPLIT_UNCOVERED` / `UNCOVERED_ARTIFACT` / `TARGET_FILE_SCOPE_ESCAPE` | Tripped `artifact_scopes` governance (v2.83) | Add details children to `:TEST` / give the artifact an owning TDD / fix target_file; or configure an exemption |

### 12.5 Landing & persistence

| Code | Cause | Recovery |
|---|---|---|
| `CHUNK_LOCKED` | Editing a committed chunk | Layer `revert` to unlock, or whole-version revert |
| `ACCEPTANCE_FAILED` | Acceptance command exited non-zero | Fix the code until tests pass |
| `HOST_DIRTY` | ~~Host repo dirty at confirm~~ | **Retired in v2.73**: confirm now commits the host repo itself and binds `code_result`; dirty is no longer a refusal |
| `CONFIRMATION_REQUIRED` | Merge without confirm | `version confirm` first |
| `CONFIRMATION_STALE` | Content changed after confirm | Re-run `version confirm` |
| `MERGE_ROLLBACK` | Merge failed midway | Already rolled back byte-for-byte; fix per `error` and retry |
| `GIT_COMMIT_FAILED` | Docs-repo commit failed | Already rolled back; fix git state and retry |
| `DUPLICATE_BASELINE_CHUNK` | add hit an existing chunk (intercepted at write time since v2.87) | Use `--action modify` |
| `MODIFY_RENAME_COLLISION` / `DUPLICATE_OVERRIDES_TARGET` | Rename/override collision | Zero disk writes; fix overrides and retry |
| `INVALID_FILE_NAME` | `--file` out of bounds | Relative path within the kind's own directory, no `.md` |
| `REVERT_PRECHECK_FAILED` / `REVERT_ANCHOR_INVALID` | Revert anchor unusable | Check the tag/commits still exist in the docs/host repos; `version backfill-tags` can rebuild missing tags |

## 13. Skill & Sub-skills

In Claude Code, use `/ait <subcommand>` directly (the `/ait:foo` colon namespace is **not
supported** — Claude Code reserves it for plugins). The main skill handles routing, the
global contract and command cheat-sheets; concrete workflows live in sub-skills:

| Sub-skill | Trigger | Purpose |
|---|---|---|

| `ait-init-guide` | `init` returns `status=incomplete` | Walks through completing global files item by item |

format spec**), `chunk-system.md`, `chunk-parser.md`, `index-system.md`,
